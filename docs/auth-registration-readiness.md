# Готовность регистраций Shectory к проду (аудит 2026-06-22, Claude)

Контекст: скоро публичный выход многих проектов; нужен поток внешних регистраций без сбоев.
Проверен код `shectory-portal/src/lib/portal-auth.ts` + `src/app/api/auth/register/*`,
`set-initial-password`, `forgot/confirm`. Источник истины — `portal_users` (см. `~/SHECTORY_AUTH_STANDARD.md`).

## ✅ Что уже хорошо

- email `@unique` — нет дублей учёток; конкурентные confirm безопасны (upsert).
- Новые внешние юзеры получают роль `user` (не admin). superadmin только `ADMIN_EMAIL`.
- Код подтверждения НЕ утекает в HTTP-ответ в проде (`debugCode` только при `NODE_ENV!=production`).
- Единый источник: новый юзер сразу доступен всем приложениям через bridge, дублировать не надо.
- Код подтверждения с TTL (`expiresAt`), одноразовый (`consumedAt`).

## 🔴 Блокеры для публичного потока (чинить до прода)

1. **Нет rate-limit на `register/request-code`.** Любой может слать неогранич. запросы кодов на
   произвольные email → email-бомбардировка, абуз SMTP, рост `portal_email_codes`. Нужен лимит
   per-IP и per-email (напр. 5/час), 429 при превышении.
2. **Нет защиты от перебора кода в `consumeEmailCode`.** 6-значный код, нет счётчика попыток/локаута
   в пределах TTL → брутфорс 10^6 за время жизни кода. Нужны: поле `attempts` на `PortalEmailCode`,
   инвалидация после N неудач, единый код на email (инвалидировать прежние при новом запросе).
3. **Код генерится `Math.random()`** (не криптостойко). Заменить на `crypto.randomInt(100000,1000000)`.

## 🟡 Риски надёжности под нагрузкой

4. **Тихий сбой SMTP в проде.** При ошибке отправки route логирует код в консоль и возвращает
   `{ok, delivery:"log"}` — юзер думает «код отправлен», но письма нет и кода он не получит.
   Нужно: при сбое SMTP отдавать ошибку юзеру (или очередь/ретрай), не делать вид что ок.
5. **`portal_email_codes` не чистится** — под потоком таблица растёт без предела. Нужен крон-клинап
   просроченных/использованных кодов (напр. ежедневно, старше 24ч).
6. **SMTP без пула соединений** — transporter создаётся на каждый вызов. Под потоком — пул/очередь.
   Плюс deliverability для внешних адресов (SPF/DKIM/DMARC для shectory.ru) проверить отдельно.
7. **Энумерация email** — `request-code` отдаёт 409 «уже зарегистрирован» → раскрывает наличие
   учётки. Для публичного прода желательно одинаковый ответ независимо от существования.
8. **CAPTCHA/anti-bot** на публичной форме регистрации отсутствует — продуктовое решение, но при
   открытии вовне почти обязательно против ботов.

## ✅ БЛОКЕР №1 (обнаружен И устранён 2026-06-22): почта НЕ доставлялась → исправлено

SMTP `mail.shectory.ru:587` (poste.io/Haraka на smain) отвергал логин `portal@shectory.ru`. Видимый симптом — `500 plugin timeout` (медленный doveadm reverse-check ~20с), но **истинная причина: НЕВЕРНЫЙ ПАРОЛЬ ящика**. `doveadm auth test` показал, что НИ пароль из `.env` (12 симв.), НИ канонический keymaster `EMAIL_PASSWORD_PORTAL` (16 симв.) не совпадали с хэшем ящика — реальный пароль дрейфанул и был неизвестен обоим. Все коды (включая Боре 21.06) оседали в логах, до юзеров не доходили.

**Фикс:** пароль ящика пересинхронизирован на значение keymaster (`doveadm pw -s SHA512-CRYPT` → UPDATE `/data/users.db`, бэкап `users.db.bak-20260622-portalpw`); `.env SMTP_PASSWORD` обновлён из keymaster (single-quote literal — у пароля спецсимволы, ломавшие парсеры; @next/env читает верно: len 16). Добавлены fail-fast SMTP-таймауты. Проверено: `doveadm auth test` → succeeded; реальная отправка Боре → `250 Message Queued`. **Сторож auth-guard теперь проверяет SMTP-логин каждые 10 мин** и алертит при рецидиве. Источник истины пароля — keymaster `EMAIL_PASSWORD_PORTAL` = ящик = `.env`.
